# Power Automate 設計（概要）

各フローの作成手順は `flows/` 配下にある。ここでは3つに分けた理由と、
全体で共通する設計方針をまとめる。

| フロー | 呼び出し元 | 役割 |
|---|---|---|
| [`YAJ-CancelFee-Submit`](../flows/YAJ-CancelFee-Submit/README.md) | `ConsentScreen`（送信）／`ErrorScreen`（再送信） | 文書番号の採番、署名画像の保存、PDF生成、SharePoint保存、メール送信 |
| [`YAJ-CancelFee-Resend`](../flows/YAJ-CancelFee-Resend/README.md) | `DetailScreen`（PDFを再送） | 保存済みPDFの再送と履歴記録 |
| [`YAJ-CancelFee-Delete`](../flows/YAJ-CancelFee-Delete/README.md) | `DetailScreen`（削除・管理者のみ） | レコード・署名画像・PDFの削除と監査記録 |

## なぜアプリではなくフローで処理するのか

Power Apps だけでは次ができないため、3工程をフローに委譲している。

1. **PDF生成** — Power Fx には PDF を作る手段がない
2. **添付付きメール送信** — Power Apps の `Office365Outlook.SendEmailV2` でも
   添付は送れるが、PDFのバイナリをアプリ側で扱う必要があり不安定
3. **採番の直列化** — Power Apps では同時実行を制御できない。
   フローの同時実行数を1に固定することで初めて重複しない採番ができる

## 設計方針1: 冪等性（要件定義 14章）

「再実行時に文書番号やPDFを重複生成しない」を、次の3段で担保している。

| 段 | 仕組み |
|---|---|
| アプリ | 送信の直前に `varRequestId` を1回だけ発番し、再実行でも同じ値を渡す |
| 採番 | `DocumentNo` が既に入っていれば採番処理をまるごとスキップする |
| PDF | `PdfUrl` が既に入っていれば生成処理をまるごとスキップする |
| メール | `Status` が既に `Sent` ならメール送信をスキップする |

結果として、エラー画面から何度「もう一度送信する」を押しても、
**失敗した工程から先だけ**が実行される。

## 設計方針2: 完了扱いにする条件（要件定義 7.4 / 14章）

```
                    ┌─ Try スコープ（採番→署名保存→PDF→保存→メール）
トリガー ─ 変数初期化 ┤
                    ├─ Catch スコープ    ← Try が「失敗/タイムアウト/スキップ」のとき
                    └─ Respond_success   ← Try が「成功した」のとき
```

`Catch` と `Respond_success` は実行条件が排他なので、1回の実行で応答は必ず1つ。
アプリは `Success = true` のときだけ完了画面へ進むため、
「全処理成功前に完了表示をしない」が構造的に保証される。

## 設計方針3: 利用者に見せる情報と記録に残す情報を分ける（要件定義 14章）

| 情報 | 利用者（エラー画面） | SharePoint 記録 |
|---|:-:|:-:|
| 失敗した工程が分かる日本語メッセージ | ○ | — |
| エラーコード（`E-FLOW-0x0`） | ○ | ○ |
| 文書番号・レコードID・受付キー・発生日時 | ○ | ○ |
| フロー実行ID | ○ | ○ |
| コネクタが返した例外文 | **×** | ○（`ErrorMessage` 列） |
| 顧客の個人情報 | — | — |

例外文をアプリに返さないのは、内部のサイトURLやスタックが顧客の目に触れる
端末に表示されるのを避けるため。管理者は `SignatureCases.ErrorMessage` と
フロー実行IDから原因を追える。

### エラーコード一覧

| コード | 失敗した工程 | 利用者向けメッセージ |
|---|---|---|
| `E-SAVE-001` | 入力内容の保存（アプリ内） | 入力内容を保存できませんでした |
| `E-SAVE-002` | 署名内容の保存（アプリ内） | 署名内容の保存に失敗しました |
| `E-FLOW-010` | レコードの取得 | 処理中にエラーが発生しました |
| `E-FLOW-020` | 文書番号の採番 | 文書番号の採番に失敗しました |
| `E-FLOW-030` | 署名画像の保存 | 署名画像の保存に失敗しました |
| `E-FLOW-040` | PDFの生成（Word テンプレート／変換） | 確認書PDFの作成に失敗しました |
| `E-FLOW-050` | PDFの保存・取得 | 確認書PDFの保存に失敗しました |
| `E-FLOW-060` | メール送信 | PDFのメール送信に失敗しました |
| `E-FLOW-000` | 上記以外 | 処理中にエラーが発生しました |
| `E-RESEND-010` | 再送（保存済みPDFなし） | 保存済みPDFがありません |
| `E-RESEND-020` | 再送（送信失敗） | 再送に失敗しました |
| `E-DELETE-010` | 削除 | 削除に失敗しました |

## 設計方針4: PDF生成の経路（要件定義 10.1）

要件定義で共有されていた「HTML → PDF で日本語が文字化けする」事象を避けるため、
**HTML を経由しない**経路を採っている。

```
フロー内で確認書のHTMLを組み立てる（Compose_Html）
   │  ・元資料の書簡形式（宛名・差出人・表題・本文・確認欄）を CSS で再現
   │  ・@page で A4縦、font-family で日本語フォントを指定
   │  ・署名PNGは data URI で埋め込む
   ▼
中間 .doc（OneDrive/YAJ-CancelFee-Temp/<文書番号>.doc）
   │  ・先頭に UTF-8 BOM を付ける。付けないと Word が文字コードを
   │    取り違えて日本語が化ける（要件定義 10.1 の事象）
   │  ・作成直後の変換は Bad gateway になることがあるため15秒待つ
   ▼
   │  OneDrive for Business「ファイルの変換」(ConvertFileByPath, type=pdf)
   │  ※ SharePoint コネクタに変換アクションは存在しない。
   │    変換できるのは OneDrive（標準）か Word Online（Premium）のみ
   ▼
署名済みPDF（SignatureDocs/<文書番号>.pdf） ← 正本
   │
   └─ 中間 .doc はフローが削除する
```

> 中間ファイルが OneDrive に置かれるため、**必ずサービスアカウントの OneDrive
> を使う**こと。個人アカウントのままだと担当者の異動・退職で経路が壊れる
> （要件定義 15.5）。

> **2026-09-16 変更**: Word テンプレート方式から **HTML→.doc 方式**に切り替えた。
> `Word Online (Business)` が Premium コネクタであり、利用者全員に
> Power Apps Premium が必要になること、および MFA 条件付きアクセス有効時に
> 動かない既知の問題があるため。現在の既定は標準コネクタのみで動く。
> 両方式の比較と切り替え方は [10 CLIデプロイ](10-cli-deployment.md) を参照。

この構成にした理由。

- **標準コネクタだけで完結する**ので追加ライセンスが要らない。
  利用者全員分の Power Apps Premium（人数 × $20/月）が不要になる
- MFA 条件付きアクセスの影響を受けない
- **CLI デプロイを完全に自動化できる**。Word テンプレート方式は
  ファイル指定に内部IDを要求するため、インポート後に画面で選び直す必要があった
- HTMLの組み立ては `scripts/flow_definitions.py` の `build_confirmation_html()`
  にあり、変更履歴が Git で追える。`scripts/preview-document.py` で
  テナント無しに出来上がりを確認できる

Word テンプレート方式も `solution/config.json` の `pdfMode` で選べる状態で残してある。
Premium ライセンスが確保でき、MFA 条件付きアクセスの問題が無いと確認できた場合は、
そちらのほうがレイアウトの自由度が高い。

## 設計方針5: 文書番号の採番（要件定義 8章）

```
日付キー（JST の yyyyMMdd）
   ↓
DocumentNumberCounter を Title で検索
   ↓ 無ければ LastNumber = 0 で作成
   ↓
読み直して LastNumber + 1 を算出
   ↓
カウンタを更新し、<日付キー>-<3桁ゼロ埋め> を文書番号にする
```

- 日付が変わると自然に `001` から始まる（キーが日付ごとに別レコードになる）
- **フローの同時実行数を1に固定**することで、読み取り→加算→書き戻しが
  直列化され、同時登録でも重複しない
- 削除しても連番は戻さない。戻すと過去に送付済みのPDFと番号が衝突する。
  欠番は許容する（`flows/YAJ-CancelFee-Delete/README.md` 参照）
- 1日1000件を超える運用になった場合は3桁では足りない。
  その時点で `formatNumber(...,'0000')` に変えるだけで対応できるが、
  過去分と桁数が混在するため、番号書式の正式決定が必要（要件定義 19章-7）
