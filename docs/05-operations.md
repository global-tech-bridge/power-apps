# 運用・障害対応手順

## 1. 同意文面を改訂する（管理者）

要件定義 11.3 のとおり、署名済みの記録には**署名時点の本文がまるごと保存されている**
（`SignatureCases.ConsentTextSnapshot`）。したがってマスタを改訂しても、
過去の記録とPDFの内容は変わらない。

### 手順

1. `ConsentMaster` リストを開く
2. **現行の行を編集しない。** 新しい行を追加する
   | 列 | 値 |
   |---|---|
   | `Title` / `ConsentId` | 現行と同じ（例 `CANCELFEE-001`） |
   | `Version` | 上げる（例 `0.9-draft` → `1.0`） |
   | `EffectiveFrom` | 適用を開始する日 |
   | `IsActive` | はい |
   | `DisplayTitle` | 画面とPDFに出す見出し |
   | `Body` | 新しい本文 |
   | `RevisedBy` / `RevisedAt` | 改訂者と日時 |
3. 現行の行の `EffectiveTo` に「新版の適用開始日の前日」を入れ、
   `IsActive` を **いいえ** にする
4. アプリを開き直して（`App.OnStart` が再実行される）、
   同意画面に新しい文面と版番号が出ることを確認する

### 注意

- `IsActive` = はい の行が複数あると、**適用開始日が最も新しいもの**が使われる。
  意図しない文面が出ないよう、改訂時は必ず旧版を `いいえ` にする
- `IsActive` = はい の行が1件も無いと、入力画面に赤い警告が出て署名へ進めなくなる
  （`E-CONSENT-000`）。これは意図した挙動（文面なしでの署名を防ぐため）
- 改訂は監査対象。`AuditLog` に `Action` = `ConsentChange` で手動記録するか、
  `ConsentMaster` にバージョン管理を有効にしておく

## 2. 組織（支社・ブロック・拠点）を変更する

`OrgMaster` リストを直接編集する。アプリ側の変更は不要。

| やりたいこと | 操作 |
|---|---|
| 拠点を追加 | 行を追加（`BranchName` / `BlockCode` / `BlockName` / `SiteCode` / `SiteName` / `IsActive` = はい / `SortOrder`） |
| 拠点を廃止 | 行を消さず `IsActive` を **いいえ** にする。過去の記録に残っている拠点名の整合性が保てる |
| 名称変更 | `SiteName` を書き換える。過去の記録は署名時の名称のまま残る（テキストで保存しているため） |

`部門マスタ.xlsx` が更新された場合は、CSVを作り直して差分を反映する。

```bash
python3 scripts/build-org-master.py 部門マスタ.xlsx data/OrgMaster.csv
```

> `販売部` と `系統推進部` には元データにブロックがないため、
> スクリプトが疑似ブロック（`販売部（ブロック未設定）` / `系統推進部（ブロック未設定）`）を
> 補完している。正式なブロック区分が決まったら、スクリプトの `PSEUDO_BLOCK` を
> 直して作り直す（`docs/07-open-issues.md` D-02）。

## 3. 管理者を追加・削除する

`AppAdmins` リストに行を追加（`UserEmail` / `UserName` / `IsActive` = はい /
`Note` に承認者と日付）。権限を外すときは行を消さず `IsActive` を **いいえ** にする。

**SharePoint 側のグループ（`YAJ-CancelFee-Admins`）への追加も必要。**
`AppAdmins` はアプリ内で削除ボタンを出すかどうかの判定にしか使っておらず、
実際に削除できるかは SharePoint の権限で決まる（`docs/04-permissions.md`）。

## 4. 障害対応

### 4-1. 利用者が「送信は完了していません」画面になった

エラー画面に出ている **エラーコード** と **文書番号／レコードID** を聞き取る。

| コード | 一次対応 |
|---|---|
| `E-SAVE-001` / `E-SAVE-002` | 端末の通信状態を確認し、もう一度送信してもらう |
| `E-FLOW-020` | 時間をおいて再送信。繰り返す場合は `DocumentNumberCounter` の当日行を確認 |
| `E-FLOW-030` | 再送信。署名を書き直してもらう |
| `E-FLOW-040` | **管理者対応が必要。** 4-2 へ |
| `E-FLOW-050` | 再送信。`SignatureDocs` の容量・権限を確認 |
| `E-FLOW-060` | 顧客メールアドレスの綴りを確認し、詳細画面から再送 |

**「もう一度送信する」を押しても二重にはならない。** 失敗した工程から先だけが
実行されるように作ってある（`docs/03-power-automate.md` 設計方針1）。

### 4-2. PDFが作られない / 文字化けする

1. Power Automate → `YAJ-CancelFee-Submit` → 実行履歴 で該当実行を開く
   （エラー画面の **フロー実行ID** で特定できる）
2. 失敗したアクションを確認する

| 失敗アクション | 原因と対処 |
|---|---|
| `Populate_template` | `DocTemplates` にテンプレートが無い／コンテンツ コントロール名が変わった。`templates/build-template.py` で再生成してアップロードし直す |
| `Populate_template`（画像欄） | 署名画像の base64 が壊れている。`SignatureImages` のPNGが開けるか確認 |
| `Convert_to_pdf` | Word Online (Business) の接続切れ、または DLP ポリシーでブロック。接続を作り直す |
| PDFが豆腐（□）になる | テンプレートのフォントが変換サーバに無い。`build-template.py` の `JP_FONT` を `MS Gothic` / `Meiryo` に変えて再生成 |

### 4-3. 同じ文書番号が2件できた

**同時実行数が1になっていない。** これが唯一の原因。

1. `YAJ-CancelFee-Submit` のトリガー → 設定 → 同時実行制御が **オン**、
   並列度が **1** になっているか確認する
2. 重複した2件のうち、後から作られた方の文書番号を管理者が手で採番し直す
   （`DocumentNumberCounter` の当日 `LastNumber` を実際の最大値に合わせる）
3. 番号を変えた側はPDFを作り直す必要がある。`PdfUrl` と `SentAt` を空にし、
   `Status` を `Signed` に戻してから、詳細画面ではなく
   フローを手動実行（`ItemID` と新しい `RequestId`）する

### 4-4. メールが届かない

1. `SendLog` で該当文書番号の行を確認する
   - `Result` = `Success` なら Power Automate 側は送信済み。
     受信側の迷惑メールフォルダ・受信拒否設定を確認する
   - 行が無い、または `Failure` ならフローの実行履歴を確認する
2. 顧客側で受信できない場合は、詳細画面の「PDFを再送」で宛先を変えて送る
   （**PDFは作り直さず保存済みのものが送られる**ので、内容は同一）

### 4-5. 一覧に出てくるはずの案件が出てこない

1. 絞り込み条件を確認する。支社・ブロック・拠点は **自分の拠点が初期表示** される。
   「条件をクリア（全国表示）」を押す
2. それでも出ない場合は件数の取りこぼしを疑う。
   アプリの 設定 → 全般 → **データ行の制限が 2000** になっているか確認する

## 5. 定期点検（月次を推奨）

- [ ] `WorkTemp` ライブラリが空であること（残っていたら変換失敗の痕跡）
- [ ] `SignatureCases` に `Status` = `Error` のまま放置された行がないこと
- [ ] `SendLog` に `Result` = `Failure` の行がないこと
- [ ] `DocumentNumberCounter` の当日以外の古い行を消していないこと（消してよいが履歴として残す方が安全）
- [ ] `ConsentMaster` の `IsActive` = はい がちょうど1件であること
- [ ] コネクタの接続が切れていないこと（Power Automate の「接続」画面）
- [ ] アプリ・フローの所有者が個人のみになっていないこと

## 6. 保管期間について（未確定）

記録・PDF・署名画像・ログの保管期間は要件定義 19章-10 のとおり未確定。
決まり次第、次のいずれかで実装する。

- SharePoint の **保持ラベル**（Microsoft Purview）を `SignatureDocs` に適用する
  — 期限まで削除できなくなるため証拠性が高い
- 期限切れレコードを抽出する定期フローを追加する

**保管期間が決まるまでは、記録を削除しない運用にすること。**
