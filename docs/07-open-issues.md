# 未確定事項と本実装での暫定判断

要件定義 19章には決定が必要な項目が20件挙げられている。実装を止めないため、
そのすべてに**暫定の実装判断**を置いた。このファイルは「何をどう仮決めしたか」と
「業務側の決定が違った場合に何を直すことになるか」の一覧である。

**変更コスト**の意味:
- **データのみ** — SharePoint のリストを直せば済む。アプリ・フローの変更なし
- **軽微** — アプリの数式1〜2箇所、またはフローの1アクション
- **中** — 画面の追加・削除、フローの分岐追加
- **大** — 設計の作り直し

## 実装の過程で追加的に判断した事項

要件定義には明示されていないが、実装するために決めざるを得なかった項目。

| # | 事項 | 暫定判断 | 判断の理由 | 変更コスト |
|---|---|---|---|:-:|
| D-01 | **「支社」に何を入れるか** | 提供された `部門マスタ.xlsx` の上位階層は `部門名`（`営業部` / `販売部` / `系統推進部`）であり、`支社` という列は存在しなかった。そのため `SignatureCases.BranchName` と `OrgMaster.BranchName` には**部門名を入れている** | 要件定義 11.2 は「支社・ブロック・拠点を親子関係で管理し、部門マスタ.xlsx を基に構成する」としているが、マスタが供給する3階層は 部門→ブロック→拠点 だった。仮に `支社` が `中部近畿支社` のような別階層を指すのであれば、`OrgMaster` の `BranchName` を書き換えるだけで対応できる（アプリ・フローの変更は不要） | データのみ |
| D-02 | **ブロックのない部門の扱い** | `販売部`（16拠点）と `系統推進部`（13拠点）は元データにブロックが無い。要件定義 7.2 はブロックを必須としているため、疑似ブロック `販売部（ブロック未設定）` / `系統推進部（ブロック未設定）` を補完した | ブロックを任意項目にすると、必須チェックと連動ドロップダウンの両方に例外分岐が入り、必須の意味が曖昧になる。疑似ブロックなら、正式なブロック区分が決まった時点で `scripts/build-org-master.py` の `PSEUDO_BLOCK` を直して作り直すだけで済む | データのみ |
| D-03 | **`拠点名` にブロック自身の行が含まれる** | 元データには各ブロックにつき1行、`拠点コード` = `ブロックコード`（拠点名が「○○ブロック」）の行がある。これはブロック事務所そのものと解釈し、拠点の選択肢として**そのまま残した** | 除外すると、ブロック事務所で受け付けた案件の登録先がなくなる | データのみ |
| D-04 | **列名を英語にした** | `SignatureCases` などの列はすべて英語名（要件定義 11.1 の表と同じ名前） | SharePoint は日本語の列名を作ると内部名が `_x9867__x5ba2__x540d_` にエスケープされ、Power Automate の OData フィルターや Word テンプレートの差し込みが読めなくなる。画面の日本語ラベルは Power Apps 側で与えている | 大（作り直し） |
| D-05 | **`PdfUrl` をハイパーリンク列ではなくテキスト列にした** | 要件定義 11.1 は「ハイパーリンク」だが、1行テキストにした | SharePoint のハイパーリンク列は Power Apps 上でレコード（`{Value, Description}`）として現れる版とテキストとして現れる版があり、環境差で数式が壊れる。`Launch()` に渡すだけならテキストで機能は同じ | 軽微 |
| D-06 | **署名完了後の編集不可の担保** | アプリ側では詳細画面に編集手段を置いていない。SharePoint 側は `SignatureCases` の項目レベル権限で「編集アクセス: ユーザーが作成した項目のみ」を推奨設定としている | 完全に編集不可にするには、利用者の権限を「閲覧」にしてレコードの作成・更新もすべてフロー経由にする必要がある（実装量が増える）。MVP では、正本である `SignatureDocs` のPDFを読み取り専用＋バージョン管理にすることで証拠性を担保している。詳細は `docs/04-permissions.md` | 中〜大 |
| D-07 | **`PdfCreated` ステータスを使っていない** | 要件定義 9章の6ステータスのうち `PdfCreated` は選択肢として作ってあるが遷移では使わず、`Stored` に集約している | PDFの作成と SharePoint への保存を1つのフロー内で連続して行うため、両者が別々に成功する状態が実際には存在しない。将来分離する場合に使える | 軽微 |
| D-08 | **再送・削除の操作者の記録** | `SendLog.SentBy` / `AuditLog.PerformedBy` は、フローの**接続ユーザー**になる（サービスアカウントに張り替えると全件同じ値になる） | 操作者を確実に残すには、フローのトリガーに `OperatorEmail` 入力を追加してアプリから渡す必要がある。各フローの手順書に追加方法を書いてある。要件定義 13章「送信者を記録する」を厳密に満たすには**この追加が必要** | 軽微（入力1つとアプリの呼び出し1行） |
| D-09 | **削除時の連番** | 削除しても `DocumentNumberCounter` の連番は戻さない（欠番を許容する） | 戻すと、削除済みの番号が別の案件に再利用され、すでに顧客へ送付済みのPDFと番号が衝突する。欠番より重複のほうが害が大きい | — |
| D-10 | **一覧のキーワード検索は前方一致** | 文書番号・顧客名・担当者の**前方一致**（`StartsWith`） | 部分一致（`in`）は SharePoint に委任できず、データ行の制限内のデータしか検索対象にならない。前方一致なら委任される。ただし3列の OR 条件のため、アプリの「データ行の制限」を 2000 にする必要がある | 軽微 |
| D-11 | **日付範囲の対象列** | 一覧の日付範囲は `RegisteredAt`（作成日）で絞る。`Created` 列を使わず独自列にした | SharePoint の `Created` 列は表示名がサイトの言語設定で変わる（日本語サイトでは「作成日時」）。Power Fx は表示名で参照するため、言語設定に依存する数式になってしまう | 軽微 |

## 本番運用の前に必ず決めること

上の表のうち、**決まらないまま本番で使うと事故になる**もの。

1. **19章-1 正式な同意文面** — 仮の文面で顧客の署名を取ってはいけない
2. **19章-18 法務・経理・税務の確認** — 収入印紙の扱い、電子署名の証拠性、
   署名済みPDFが必要な証拠性を満たすか
3. **19章-10 保管期間** — 決まるまで記録を削除しない運用にする
4. **19章-15 メール送信元アカウント** — 顧客に見えるアドレス
5. **19章-16 利用対象者** — 誰にアプリを共有するか
6. **D-01 「支社」の定義** — PDFと一覧に印字される項目なので、
   部門名で正しいかを確認する
