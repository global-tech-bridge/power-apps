# 未確定事項と本実装での暫定判断

要件定義 19章には決定が必要な項目が20件挙げられている。実装を止めないため、
そのすべてに**暫定の実装判断**を置いた。このファイルは「何をどう仮決めしたか」と
「業務側の決定が違った場合に何を直すことになるか」の一覧である。

## 2026-09-09 更新: 元資料2点を受領した

要件定義の作成時点では取得できなかった添付2点を受領し、内容を反映した。

| `整備キャンセル料について.pptx`（2026-06-02 サービス事業推進部） | この書面の位置づけ、運用方針、上申時の懸案5点 |

### pptx から判明した位置づけ

- この書面は **「確認書」** である。「事前説明を行ったことを**確認**する『確認書』を
  支社として設定したい」（スライド3）。docx の署名欄の文も
  **「私は上記内容について確認いたしました。」** で、「同意します」ではない
- **使用は任意**。「基本的にトラブルになりそうなお客様や案件について活用いただく」（スライド3）
- 業務の流れは「整備ご用命の際に、お客様へ整備料金説明と合わせてご確認いただき、
  了承・ご署名の上、整備機をお預かりしてお見積りに移る」（スライド3）。
  要件定義 6章の想定と一致している
- 背景は 2026年5月 天理支店の事例。事前にキャンセル料を説明していたにもかかわらず
  「そのような説明を聞いていない」とトラブルになった（スライド2）

### pptx スライド3「上申にあたり懸案」— 5点すべて未解決

1. 文面について問題ないかご意見を賜りたい
2. 署名欄について過不足が無いか
3. 当該書面の保管期限や保管方法についてのルール
4. 署名を求めるにあたり、**収入印紙を貼付する必要があると推定される**
5. そもそも既存の仕組みで代替できるものが無いか

つまり**文面そのものが上申中**である。版 `1.0` として登録しているのは
「支社が起案した正式文面」という意味であり、**社内承認が完了した版ではない**。

**変更コスト**の意味:
- **データのみ** — SharePoint のリストを直せば済む。アプリ・フローの変更なし
- **軽微** — アプリの数式1〜2箇所、またはフローの1アクション
- **中** — 画面の追加・削除、フローの分岐追加
- **大** — 設計の作り直し

## 実装の過程で追加的に判断した事項

要件定義には明示されていないが、実装するために決めざるを得なかった項目。

| # | 事項 | 暫定判断 | 判断の理由 | 変更コスト |
|---|---|---|---|:-:|
| D-01 | **「支社」に何を入れるか** | 提供された `部門マスタ.xlsx` の上位階層は `部門名`（`営業部` / `販売部` / `系統推進部`）であり、`支社` という列は存在しなかった。そのため `SignatureCases.BranchName` と `OrgMaster.BranchName` には**部門名を入れている** | 要件定義 11.2 は「支社・ブロック・拠点を親子関係で管理し、部門マスタ.xlsx を基に構成する」としているが、マスタが供給する3階層は 部門→ブロック→拠点 だった。仮に `支社` が `中部近畿支社` のような別階層を指すのであれば、`OrgMaster` の `BranchName` を書き換えるだけで対応できる（アプリ・フローの変更は不要） | データのみ |
| D-02 | **ブロックのない部門の扱い** | `販売部`（16拠点）と `系統推進部`（13拠点）は元データにブロックが無い。要件定義 7.2 はブロックを必須としているため、疑似ブロック `販売部（ブロック未設定）` / `系統推進部（ブロック未設定）` を補完した | ブロックを任意項目にすると、必須チェックと連動ドロップダウンの両方に例外分岐が入り、必須の意味が曖昧になる。疑似ブロックなら、正式なブロック区分が決まった時点で `scripts/build-org-master.py` の `PSEUDO_BLOCK` を直して作り直すだけで済む | データのみ |

| D-14 | **元資料の重複誤字を修正した** | 元資料の表見出しは「組戻し**せずせず**そのままお返し」（「せず」が重複）。本実装では「組戻しせずそのままお返しする場合」と1回にしている | 顧客が署名する文書に明らかな誤字を再現するのは不適切と判断した。**元資料を修正すべき箇所**として報告対象。元資料側を直す場合は、こちらの表記と一致していることを確認する | データのみ |

| D-16 | **元資料の署名欄に無い「機番」「整備区分」をPDFの確認欄に追加した** | 元資料の署名欄は 型式／ご用命事項／日付／ご署名 の4つ。PDFの確認欄はこれに **機番／整備区分／お名前** を加えた7行にしている | 要件定義 10章がPDFの記載項目として機番・整備区分を求めているため。ただし pptx スライド3の懸案2「署名欄について過不足が無いか」が未確定なので、**増やしすぎている可能性がある**。不要と決まれば行を消すだけ | 軽微（テンプレート） |

## 本番運用の前に必ず決めること

上の表のうち、**決まらないまま本番で使うと事故になる**もの。

1. **確認文面の上申結果**（19章-1 / pptx 懸案1）— 現在登録しているのは
   2026-06-02 の支社起案版。**社内承認が完了した文面ではない**
2. **収入印紙の取扱い**（19章-18 / pptx 懸案4）— pptx が「貼付する必要があると
   推定される」と明記している。電子交付にした場合の扱いを所管部門に確認する
3. **署名欄の過不足**（19章-2 / pptx 懸案2）— 本実装はPDFの確認欄を
   元資料の4行から7行に増やしている（D-16）。妥当か確認する
4. **保管期間と保管方法**（19章-10 / pptx 懸案3）— 決まるまで記録を削除しない運用にする
5. **既存の仕組みでの代替可否**（19章-20 / pptx 懸案5）
6. **19章-15 メール送信元アカウント** — 顧客に見えるアドレス
7. **19章-16 利用対象者** — 誰にアプリを共有するか
8. **D-01 「支社」の定義** — PDFと一覧に印字される項目なので、
   部門名で正しいかを確認する
9. **D-14 元資料の誤字** — 「組戻しせずせず」の重複。元資料側の修正が必要
