# 権限設計

要件定義 5章（ユーザーと権限）／12章（一覧の閲覧範囲）／15.3（セキュリティ・個人情報）
／17.4（受入条件）に対応する。

## 前提: 未確定事項があるため「削除のみ管理者」方式で実装している

要件定義 12章では、閲覧範囲について次の3案が挙げられ、どれを採るかは未確定だった。

1. ロール別の範囲制御
2. 組織単位の範囲制御
3. **全利用者参照可とし、削除のみ管理者に限定**

MVP では **3** を採った。理由は次の3点。

- 1 と 2 は「誰がどの範囲を見られるか」の業務ルールが決まっていないと実装できない
  （要件定義 19章-8 が未確定）
- SharePoint の項目レベル権限で範囲を絞ると、Power Apps の一覧が委任できなくなり、
  件数が増えたときに取りこぼす
- 3 なら、後から 1 や 2 に移行する際にアプリ側の作り直しが要らない
  （`OperatorEmail` / `BranchName` / `BlockName` / `SiteName` を列に持たせてあり、
  絞り込み条件を足すだけで済む）

ただし **「全社一律閲覧」ではない**。アプリを使えるのは下記のセキュリティグループの
メンバーだけであり、SharePoint サイト自体もプライベートにしている。

一覧画面では、支社・ブロック・拠点の絞り込みが **自分の拠点で初期表示** される。
「全国を見る」には明示的に条件をクリアする操作が必要なので、
日常的には自拠点の案件だけが見える状態になる。

## SharePoint のアクセス権

サイトの共有設定から、既定の「メンバー」「ビジター」グループではなく、
用途別のグループを使う。

| 対象 | グループ | 権限 | 備考 |
|---|---|---|---|
| アプリ利用者（営業・サービス担当） | `YAJ-CancelFee-Users` | **投稿** | リストへの追加・自分の下書き編集に必要 |
| 管理者 | `YAJ-CancelFee-Admins` | **フル コントロール** | 削除・マスタ保守 |
| フローの実行アカウント | サービスアカウント | **フル コントロール** | PDF作成・ファイル削除に必要 |
| 上記以外 | — | **なし** | 個人情報・署名PDFへアクセスさせない（要件定義 17.4） |

### ライブラリの権限を個別に絞る

`SignatureDocs`（署名済みPDFの正本）は、利用者が内容を編集できてはいけない
（要件定義 17.2「署名後の内容が通常利用者により編集できない」）。

1. `SignatureDocs` → 設定 → **このドキュメント ライブラリの権限**
2. **権限の継承を中止**
3. `YAJ-CancelFee-Users` の権限を **閲覧（読み取り）** に変更
4. サービスアカウントは **フル コントロール** のまま

`SignatureImages` も同様に利用者は読み取りのみにする。
`WorkTemp` は利用者に権限を与えない（フローだけが使う）。

> 利用者が「投稿」権限を持っていても、PDFライブラリが読み取り専用であれば
> 正本を書き換えられない。バージョン管理も有効にしてあるため、
> 万一の上書きも復元できる。

### マスタリストの権限

| リスト | 利用者 | 管理者 |
|---|---|---|
| `SignatureCases` | 投稿（自分の作成分の編集） | フル コントロール |
| `OrgMaster` | 閲覧 | フル コントロール |
| `ConsentMaster` | 閲覧 | フル コントロール |
| `AppAdmins` | 閲覧 | フル コントロール |
| `SendLog` | 権限なし（フローのみ） | 閲覧 |
| `AuditLog` | 権限なし（フローのみ） | 閲覧 |
| `DocumentNumberCounter` | 権限なし（フローのみ） | 閲覧 |

`ConsentMaster` を利用者に書かせないのは、同意文面が勝手に変わると
証拠性が損なわれるため。**同意文面の改訂は管理者だけが行う。**

## アプリ内の権限判定

アプリは `AppAdmins` リストで管理者を判定している（`App.OnStart`）。

```
Set(varIsAdmin, CountRows(Filter(colAdmin, Lower(UserEmail) = varUserEmail)) > 0)
```

`varIsAdmin` が制御しているのは次の3つ。

| 対象 | 通常利用者 | 管理者 |
|---|:-:|:-:|
| 詳細画面の「削除」ボタン | 非表示 | 表示 |
| エラー詳細（例外文）の表示 | 非表示 | 表示 |
| 記録済みエラーコードの表示 | 非表示 | 表示 |

### これはUI上の制御であり、権限の実体は SharePoint 側

`AppAdmins` に載っていない利用者に削除ボタンは見えないが、
SharePoint 側で「投稿」権限を持っていればリスト画面から直接削除できてしまう。
**権限の実体は SharePoint のアクセス権**であり、アプリ側は操作導線を隠すだけ。

要件定義 17.4「一般利用者は署名完了記録を編集・削除できない」を厳密に満たすには、
次のいずれかが必要。未確定事項として `docs/07-open-issues.md` D-06 に記載。

- SharePoint の項目レベル権限で「自分が作成した項目のみ編集」に設定し、
  さらに署名完了後はフローで項目の権限を読み取り専用に落とす
- 利用者の権限を「閲覧」にし、レコードの作成・更新もすべてフロー経由にする
  （実装量は増えるが最も堅い）

MVP では前者の簡易版として、リストの詳細設定で
**「項目レベルのアクセス許可」→「読み取りアクセス: ユーザーが作成した項目のみ」は
使わない**（一覧の閲覧範囲要件と衝突するため）、
**「編集アクセス: ユーザーが作成した項目のみ」を設定する**ことを推奨する。

1. `SignatureCases` → 設定 → **詳細設定**
2. 項目レベルのアクセス許可 → 編集アクセス → **ユーザーが作成した項目のみ**
3. 読み取りアクセスは **すべての項目** のまま（一覧を全員が見られるようにするため）

## 管理者の定義（要件定義 19章-9 が未確定）

「管理者」を誰にするかは業務側の決定事項。実装上は `AppAdmins` リストに
メールアドレスを追加するだけで付与できるようにしてある。

暫定の運用案。

- 支社ごとに1〜2名の管理者を置く
- 管理者の追加・削除は `AppAdmins` リストで行い、`Note` 列に承認者と日付を記録する
- `IsActive` を `いいえ` にすれば、行を消さずに権限を外せる（履歴が残る）
